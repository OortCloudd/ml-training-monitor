# ML performance engineering

Produce a measured explanation of where training time goes, followed by the smallest justified optimization. GPU utilization is an observation, not the objective. A GPU at 99% can still be compute-limited, memory-limited, executing many inefficient small kernels, or waiting within poorly scheduled kernels; classify from throughput and timeline evidence, not activity alone. Optimize useful throughput or time to a fixed quality under the user's accepted numerical/scientific contract.

## Routine

Use this as a task checklist, marking steps done, unnecessary, or blocked with evidence. Scale the work to the question; do not install a distributed stack for a one-GPU problem.

1. **Identify the actual run.** Verify PID, service, executable/environment, working directory, revision and dirty state, active config, checkpoint and logging semantics. Resolve old notes against live state. Define throughput units (images, tokens, batches, optimizer updates); variable shapes make updates/s alone insufficient.
2. **Fix the measurement contract.** Record batch and effective microbatches, accumulation, input shapes/token distributions, precision, optimizer, seed/source order, threads, GPU assignment, libraries and other workloads. Read the actual launcher's bootstrap as well as its training function: environment variables, affinity, allocator and per-process memory policies can change timing without changing model outputs. Compare the live process settings with the replay before accepting a baseline. Importing a helper function does not execute its CLI setup. Separate exact execution changes from changes to model/data/precision/optimizer/quality. A larger effective batch is not a free speed optimization.
3. **Observe production first.** Read existing progress and latency logs plus a time series of hardware activity. Report sample count, window, mean/median/p95, variability, first/warmup exclusions and checkpoint/validation costs. Inspect storage capacity before writing traces. Avoid raw process arguments, identifiers and tensors in exported artifacts.
4. **Map one complete step.** Input/storage → decode/augment → ready queue → packing/grouping → host-to-device transfer → forward/loss → backward → gradient checks/clipping → optimizer → logging/checkpoint/validation. Classical CPU ML also needs preprocessing/fit/predict/CV separation, BLAS/joblib thread counts and oversubscription checks. Read [measurement.md](measurement.md) for timing and attribution rules. For activity-versus-efficiency questions, temporal GPU monitoring, SOL metrics, roofline analysis or periodic profiling, use [gpu-efficiency.md](gpu-efficiency.md).
5. **Trace the unresolved part.** Start with the least intrusive method that answers the question. Use CPU sampling for host work; framework or Nsight timelines for dispatch, kernels and copies. Capture a short warmed representative window. Do not add synchronization after every stage to an overlap benchmark. Record profiler overhead against an unprofiled replay. Missing GPU events mean missing evidence, not zero GPU activity.
6. **Identify the critical path and fast-path coverage.** Distinguish producer time from consumer wait, inclusive host time from active CPU work, memory capacity from bandwidth, GPU duty cycle from SM occupancy/FLOP efficiency, and CPU gaps from launch-bound small workloads. Measure actual grouping sizes: configured microbatch 16 does not guarantee groups of 16. When graphs, compilation, caching or shape-specific kernels select different paths, record their actual use and fallbacks by shape. Inspect work outside the captured boundary, including gradient accumulation. Use representative time windows first, then supported Nsight SOL/roofline, memory-hierarchy, occupancy and scheduler counters where necessary; label unavailable counters and dated profiles explicitly. Compare their fractions of calls, samples/tokens and step wall time; optimizing most samples can still leave most time untouched. Treat `.item()`, `.cpu()`, bool conversion, checks and copies as hypotheses until trace evidence supports them.
7. **Test one cause at a time.** Select a bounded A/B or ABBA experiment using equivalent inputs, initial model/optimizer/RNG, warmup and co-resident load. Account for end-of-pipeline drain effects. Preserve and compare outputs, loss, gradients, final state and resume behavior to the standard appropriate to the proposed change. Never suppress checks or alter tests to obtain a speedup. An instrumented trace is not a production throughput benchmark.
8. **Decide and verify.** Report the cause, measured fraction of the critical path, likely remedy, observed gain or untested hypothesis, and uncertainty. Deploy only within authorized scope; keep the last known-good checkpoint/config and a concrete recovery path. Recheck live progress, memory, errors and throughput after deployment. If integration changes a candidate to preserve correctness, its old speedup is not the deployed result: remeasure the integrated path. A diagnosis-only request ends with findings, not an unsolicited training change.
9. **Close the performance loop.** Successful deployment verifies operation; it does not establish that the requested optimization effort is complete. For an ongoing throughput-improvement task, retrace the exact deployed path, attribute the largest remaining avoidable cost, and choose the next experiment from that evidence. Do not stop solely because one change helped or utilization is stable, and do not reuse the old bottleneck explanation without checking whether it moved. Stop at the requested scope/budget, or explain why the remaining measured costs do not justify another intervention under the user's constraints. Do not turn a narrow fix into an open-ended tuning campaign or chase 100% GPU activity as the objective.

## Active training and bounded replays

Inspection does not authorize stopping unrelated workloads. If tracing requires a pause, determine whether the user's request already covers a bounded profiling interruption. Prepare and validate all instrumentation and recovery first. Use the project's verified graceful stop that commits an update, not a blind restart. Preserve the exact durable checkpoint, run a separate replay on the freed GPU, never promote replay weights, then resume the unchanged production configuration even if profiling fails. If that cannot be done under existing authorization, finish passive diagnostics and ask about the concrete remaining operation.

Do not benchmark concurrently on a GPU occupied by production and present the result as isolated. Never infer permissions from old agent prescriptions. Keep profiling artifacts local for sensitive work.

## Deliverable

A compact report with run/config identity, observation window, throughput, a phase/timeline breakdown, the bottleneck evidence, profiler limitations, and the next specific intervention. After deployment, separate the gain achieved from the residual bottleneck and the reason for continuing or stopping. Include fast-path/fallback coverage when it explains the residual cost, plus the trace and commands needed to reproduce the measurement. State explicitly which results are measured, inferred or not tested. Do not claim access to a company's private training practices.

Use `scripts/summarize_trace.py TRACE.json --output summary.json` for a PyTorch Chrome trace with `perf::step` ranges. It clips real kernel/copy events to each step and merges overlapping intervals; it excludes annotations from GPU time. Its outputs are device activity and inclusive host annotations, not SM occupancy or additive CPU+GPU percentages.

Sources and candidate-skill selection are in [sources.md](sources.md). This investigation routine does not require deploying another dashboard or monitoring service; use the existing ML Training Monitor integration.
