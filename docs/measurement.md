# Measurement rules

- Verify launch parity, not just tensor parity. For Linux workloads, record applicable `/proc/PID/status` fields (including `THP_enabled` and CPU affinity), selected thread/allocator environment settings and launcher calls such as `prctl`. A replay missing a production-only memory policy cannot establish a production speedup, even if final weights match. Adopt the observed policy for that comparison; do not turn a project's THP choice into a universal requirement. If a mismatch is discovered, retain the raw evidence, mark the affected timing claims as superseded and rerun the required comparison.

- For latency, use synchronized boundaries or CUDA events with explicit stream semantics. Host timers around asynchronous calls measure submission plus any incidental waits. For overlapped throughput, time a sequence with boundary synchronization, not each operator.
- Warm context creation, allocator, compilation and algorithm selection separately. Count actual measured steps and shapes; report variance and percentiles. Include periodic work when estimating time-to-finish.
- Exclude pipeline drain according to the actual lookahead depth. With two prepared batches ahead, excluding only the last step can still leave a penultimate step benefiting from reduced producer contention. Check the timeline instead of applying a fixed one-step exclusion to every pipeline.
- Producer preparation time may overlap most of a step. Only time the consumer waits for the prepared batch contributes directly to a stall; a near-zero wait does not rule out CPU contention with kernel dispatch.
- CPU utilization summed over threads can exceed 100%; state cores-equivalent or percent of whole machine. Affinity is permission to use cores, not parallelism. Check nested joblib/OpenMP/BLAS pools and memory/NUMA locality before adding workers.
- GPU utilization from nvidia-smi is the fraction of a sampling interval with kernel execution. It is not a measure of FLOP efficiency, SM occupancy or tensor-core saturation. GPU memory allocated measures capacity, not bandwidth.
- Framework CPU operator durations include waiting. A long `aten::to`, bool conversion or synchronization can be waiting on previously queued kernels. Correlate CPU and device lanes; do not call the full host duration transfer cost.
- Chrome trace categories `kernel`, `gpu_memcpy`, `gpu_memset` contain device activity. `user_annotation`, `gpu_user_annotation`, `ProfilerStep` and named phase markers are ranges, not kernels. Use the union of clipped device intervals per device and step. Do not add nested inclusive ranges, overlapping streams, or CPU+GPU sums as if they partition wall time.
- Gaps in the device timeline have multiple possible causes: host dispatch, blocking copies, locks/GIL, synchronization, source starvation, distributed collectives or interference. Attribute using aligned host traces and a controlled intervention. If CPU sampling is unavailable, state the limit.
- Break down conditional execution by the shapes that actually occurred. Annotate group boundaries and graph/compiled/fallback calls; report sample or token share alongside inclusive wall-time share. For example, 48 images in captured groups and 16 in uncaptured groups does not mean 75% of the time is optimized: those remaining 16 can dominate the step. Use this to prioritize the slow remainder, not to assume a speedup for an untested extension. Inclusive group timing can contain GPU work issued earlier; state that limitation.
- Extending graph coverage needs an explicit memory budget and checks for reused gradient buffers, evaluation mode and checkpoint resume. Do not silently pad, regroup samples or reorder gradient accumulation to fit a fast path and call it equivalent.
- Validate prepared tensors, masks and index plans independently of loss and final-state parity when execution changes preprocessing. BF16 computation can hide small differences in FP32 inputs; equal weights from a bounded replay alone do not establish identical image preparation. If preserving inputs requires a different integrated variant, remeasure that variant.
- Use shape recording, stacks and memory traces only when needed; they increase overhead and trace size. Start with short CPU/CUDA profiling windows and lightweight annotations. Keep real input tensors and sample identifiers out of metadata.
- For distributed work, compare per-rank step timelines, collective wait, stragglers and interconnect. Do not recommend changing parallelism for a single-device job without measured need.
- Preserve diagnostics that establish training validity. If they are costly, consider equivalent batching or changing execution placement, then verify behavior. Lower monitoring frequency is a user-visible tradeoff and cannot masquerade as an equivalent optimization.

- Autograd may run backward and accumulation on CPU worker threads. Filtering all CPU events to the thread containing `perf::step` can hide most gradient clones and `AccumulateGrad` calls. Inspect matching process events on worker threads inside the step window; keep counts and inclusive durations separate from the main-thread timeline, and do not sum overlapping threads or nested copy/clone ranges as elapsed time.
- Complete coverage of selected blocks does not imply a fully captured update: leaf-gradient hooks, accumulation, loss plumbing and optimizer work can remain outside graphs. Trace an update with fully covered blocks to expose this residual before proposing more shapes or a whole-step fusion. More cached shapes may increase coverage and VRAM without improving throughput; use repeated matched measurements rather than the best repetition. Record both admission guards and observed peak allocated/reserved memory, since a pre-capture admission limit does not cap later training peaks.
